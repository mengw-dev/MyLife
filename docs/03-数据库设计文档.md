## 1. 数据库设计原则

1. 所有个人业务数据通过 `user_id` 关联用户。
2. 时间线不建立独立业务数据表。
3. 日记、知识笔记、学习记录和重要事件分别存储。
4. 知识笔记与学习记录一对多关联。
5. 照片文件独立存储，数据库只保存文件信息。
6. 标签通过关联表与业务数据建立多对多关系。
7. 通过外键和索引保证基本数据完整性。
8. 通过 Service 层保证跨用户关联安全。

数据库统一使用：

```sql
CHARACTER SET utf8mb4
COLLATE utf8mb4_0900_ai_ci
```

主键统一使用：

```sql
BIGINT UNSIGNED AUTO_INCREMENT
```

## 3. 数据表详细设计

### 3.1 t_user 用户表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| username | VARCHAR(32) | 用户名，唯一 |
| password_hash | VARCHAR(255) | BCrypt 密码哈希 |
| nickname | VARCHAR(64) | 昵称 |
| status | TINYINT | 用户状态 |
| last_login_at | DATETIME(3) | 最后登录时间 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

唯一索引：

```sql
uk_user_username(username)
```

### 3.2 life_stage 人生阶段表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| name | VARCHAR(100) | 阶段名称 |
| start_date | DATE | 开始日期 |
| end_date | DATE | 结束日期，可空 |
| description | TEXT | 阶段介绍 |
| cover_media_id | BIGINT | 封面照片，可空 |
| sort_order | INT | 排序 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

规则：

- `start_date` 必须小于或等于 `end_date`。
- `end_date` 为空表示持续中。
- 允许阶段日期重叠。
- 删除阶段后关联业务记录的 `stage_id` 置空。

### 3.3 year_profile 年度资料表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| year | SMALLINT | 年份 |
| title | VARCHAR(120) | 年度标题 |
| summary | TEXT | 年度简介 |
| cover_media_id | BIGINT | 代表照片 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

唯一索引：

```sql
UNIQUE(user_id, year)
```

没有年度资料时，系统仍然可以通过业务数据生成年份总览。

### 3.4 diary 日记表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| stage_id | BIGINT | 人生阶段，可空 |
| title | VARCHAR(200) | 标题 |
| content | LONGTEXT | 正文 |
| record_date | DATE | 记录日期 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

索引：

```sql
(user_id, record_date, id)
(user_id, stage_id, record_date)
```

同一天允许多篇日记。

### 3.5 knowledge_category 知识分类表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| parent_id | BIGINT | 父分类，可空 |
| name | VARCHAR(100) | 分类名称 |
| sort_order | INT | 排序 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

通过 `parent_id` 实现多级分类。

索引：

```sql
(user_id, parent_id, sort_order)
```

### 3.6 knowledge_note 知识笔记表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| category_id | BIGINT | 所属分类 |
| title | VARCHAR(200) | 标题 |
| content_markdown | LONGTEXT | Markdown 内容 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

索引：

```sql
(user_id, category_id, updated_at, id)
```

### 3.7 study_record 学习记录表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| note_id | BIGINT | 关联知识笔记，可空 |
| note_title_snapshot | VARCHAR(200) | 笔记标题快照 |
| stage_id | BIGINT | 人生阶段，可空 |
| title | VARCHAR(200) | 学习标题 |
| content | LONGTEXT | 学习内容 |
| understanding | LONGTEXT | 当时理解 |
| questions | LONGTEXT | 遇到的问题 |
| study_date | DATE | 学习日期 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

索引：

```sql
(user_id, study_date, id)
(user_id, note_id, study_date)
```

知识笔记删除后：

```sql
note_id = NULL
```

但保留 `note_title_snapshot`。

### 3.8 important_event 重要事件表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| stage_id | BIGINT | 人生阶段，可空 |
| diary_id | BIGINT | 关联日记，可空 |
| title | VARCHAR(200) | 事件标题 |
| description | LONGTEXT | 事件描述 |
| event_date | DATE | 事件日期 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 修改时间 |

索引：

```sql
(user_id, event_date, id)
```

删除日记后，事件保留，`diary_id` 置空。

### 3.9 media_file 媒体文件表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| user_id | BIGINT | 所属用户 |
| storage_key | VARCHAR(255) | 服务端生成的文件存储标识 |
| original_name | VARCHAR(255) | 原始文件名 |
| mime_type | VARCHAR(100) | 文件 MIME |
| size_bytes | BIGINT | 文件大小 |
| sha256 | CHAR(64) | 文件校验值 |
| width | INT | 图片宽度 |
| height | INT | 图片高度 |
| description | VARCHAR(500) | 照片描述 |
| created_at | DATETIME(3) | 上传时间 |

索引：


数据库不保存图片二进制。

### 3.10 tag 标签表

| 字段 | 类型 | 说明 |
| --- | --- | --- |

| name | VARCHAR(50) | 标签名称 |
| created_at | DATETIME(3) | 创建时间 |


## 6. 重要数据库约束

### 6.1 外键

所有业务表的 `user_id` 关联 `t_user.id`。

其他关联：

- `diary.stage_id` → `life_stage.id`
- `study_record.note_id` → `knowledge_note.id`
- `study_record.stage_id` → `life_stage.id`
- `important_event.stage_id` → `life_stage.id`
- `important_event.diary_id` → `diary.id`
- `knowledge_note.category_id` → `knowledge_category.id`

### 6.2 删除策略

| 删除对象 | 处理方式 |
| --- | --- |
| 人生阶段 | 关联记录 `stage_id` 置空 |
| 知识笔记 | 学习记录 `note_id` 置空，保留标题快照 |
| 知识分类 | 存在子分类或笔记时禁止删除 |
| 日记 | 事件 `diary_id` 置空 |
| 照片 | 存在引用时禁止删除 |
| 标签 | 删除关联后可清理无引用标签 |
| 用户 | 通过专门的注销业务清理全部数据和文件 |

### 6.3 数据隔离

必须注意：

外键只能保证 ID 存在，不能保证两个关联对象属于同一个用户。

因此，Service 层必须校验：

- 关联的人生阶段属于当前用户。
- 关联的知识笔记属于当前用户。
- 关联的日记属于当前用户。
- 关联的照片属于当前用户。
- 关联的标签属于当前用户。

**禁止只凭客户端传入的 ID 建立关联。**

## 7. 数据库索引规范

所有个人业务表必须对 `user_id` 建立有效索引。

重点索引：

```sql
diary:
(user_id, record_date, id)

study_record:
(user_id, study_date, id)
(user_id, note_id, study_date)

important_event:
(user_id, event_date, id)

knowledge_note:
(user_id, category_id, updated_at)

life_stage:
(user_id, start_date, end_date)
```

第一版使用 MySQL LIKE 查询搜索。

暂时不引入 Elasticsearch。

## 8. Flyway 迁移规范

数据库结构全部通过 Flyway 管理。

迁移文件：

```text
src/main/resources/db/migration/
├── V1__init_schema.sql
├── V2__add_xxx.sql
└── V3__modify_xxx.sql
```

规则：

1. 已经执行过的迁移文件禁止修改。
2. 数据库结构变更必须新增迁移文件。
3. 每次迁移都必须在 MySQL 8 环境验证。
4. 不允许依赖 Hibernate 自动建表。
5. 生产环境不允许随意手动修改数据库结构。

**注意：数据库设计文档是结构基线，实际 SQL 以经过 MySQL 8 验证的 Flyway 迁移文件为准。**
