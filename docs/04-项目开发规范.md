## 1. 项目技术规范

### 1.1 后端

- Java 21
- Spring Boot 3
- Spring Security 6
- MyBatis-Plus
- MySQL 8
- Flyway
- Maven
- JUnit 5

### 1.2 前端

- Vue 3
- TypeScript
- Vite
- Vue Router
- Pinia
- Element Plus
- Axios

### 1.3 架构要求

采用单体架构。

后端统一使用：

```text
Controller → Service → Mapper → MySQL
```

禁止在第一版引入：

- 微服务。
- Redis。
- RabbitMQ。
- Elasticsearch。
- Kubernetes。
- JWT。

## 3. 分层职责

### 3.1 Controller

负责：

- 接收 HTTP 请求。
- 参数校验。
- 调用 Service。
- 返回统一响应。

禁止：

- 编写复杂业务逻辑。
- 直接操作数据库。
- 直接操作文件系统。

### 3.2 Service

负责：

- 业务逻辑。
- 数据权限校验。
- 事务管理。
- 多个 Mapper 之间的协调。
- 业务规则判断。

复杂业务必须放在 Service 层。

### 3.3 Mapper

负责：

- 数据库查询。
- 数据插入。
- 数据修改。
- 数据删除。
- 分页查询。
- 聚合查询。

复杂 SQL 可以使用 XML。

### 3.4 Entity

负责映射数据库表。

不直接作为接口请求对象或响应对象。

### 3.5 DTO

负责接收前端请求。

使用 Jakarta Validation 进行参数校验。

### 3.6 VO

负责向前端返回数据。

不能直接暴露：

- `password_hash`。
- 文件绝对路径。
- Session 信息。
- 内部敏感配置。

## 4. 命名规范

| 类型 | 命名方式 | 示例 |
| --- | --- | --- |
| 类名 | UpperCamelCase | DiaryService |
| 方法 | lowerCamelCase | createDiary |
| 字段 | lowerCamelCase | recordDate |
| 常量 | UPPER_SNAKE_CASE | MAX_FILE_SIZE |
| 数据表 | snake_case | study_record |
| 数据库字段 | snake_case | created_at |
| 请求 DTO | XxxRequest | CreateDiaryRequest |
| 响应 VO | XxxVO | DiaryVO |

统一使用英文命名。

## 5. Spring Security 规范

使用 Session 认证。

### 5.1 登录流程

```text
前端提交用户名和密码
        ↓
AuthenticationManager
        ↓
AuthenticationProvider
        ↓
UserDetailsService
        ↓
PasswordEncoder 校验密码
        ↓
认证成功
        ↓
SessionAuthenticationStrategy
        ↓
保存 SecurityContext
        ↓
返回登录成功
```

### 5.2 安全要求

1. 使用 BCrypt。
2. 开启 CSRF 防护。
3. 使用 Session。
4. 登录成功后执行 Session 固定攻击防护策略。
5. 正确保存 SecurityContext。
6. 登出时销毁 Session。
7. 当前用户信息通过 SecurityContext 获取。

特别注意：

如果使用自定义登录 Controller，不能只调用 `AuthenticationManager.authenticate()`，还必须正确处理 `SessionAuthenticationStrategy` 和 `SecurityContextRepository`。

### 5.3 数据隔离

建立统一的当前用户获取工具：

```java
CurrentUser.getUserId()
```

所有业务 Service 获取当前用户 ID。

例如：

```java
Long userId = currentUser.getUserId();
```

数据库查询：

```sql
SELECT *
FROM diary
WHERE id = #{id}
AND user_id = #{userId};
```

禁止：

```sql
SELECT *
FROM diary
WHERE id = #{id};
```

对于个人数据，任何查询、修改、删除操作都必须考虑用户归属。

关联资源也必须逐一校验归属。

## 6. 统一响应规范

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

失败响应：

```json
{
  "code": 40001,
  "message": "参数错误",
  "data": null
}
```

所有异常由 `GlobalExceptionHandler` 统一处理。

业务异常使用 `BusinessException`。

禁止直接将异常堆栈返回给前端。

## 7. 参数校验

使用：

- `@NotNull`
- `@NotBlank`
- `@Size`
- `@Min`
- `@Max`
- `@Valid`

例如：

```java
public record CreateDiaryRequest(

    @NotBlank
    @Size(max = 200)
    String title,

    @NotBlank
    String content,

    @NotNull
    LocalDate recordDate

) {}
```

Controller 必须使用 `@Valid`。

## 8. 数据库与事务规范

1. 使用 MyBatis-Plus。
2. 简单 CRUD 使用 BaseMapper。
3. 复杂查询可以使用 XML。
4. 所有数据库结构变更使用 Flyway。
5. 多表写入必须使用事务。
6. 删除操作必须遵循数据库设计文档。
7. 不允许在 Controller 中操作 Mapper。
8. 禁止使用字符串拼接构造 SQL。
9. 分页查询必须限制最大页大小。
10. 避免 N+1 查询。

例如：

```java
@Transactional(rollbackFor = Exception.class)
public void createDiary(CreateDiaryRequest request) {
    // 业务逻辑
}
```

## 9. 文件上传规范

1. 文件名由服务端生成 UUID。
2. 不允许使用客户端文件名作为存储路径。
3. 校验文件扩展名。
4. 校验 MIME 类型。
5. 校验文件真实签名。
6. 限制文件大小。
7. 文件保存在非公开目录。
8. 下载前检查当前用户权限。
9. 数据库只保存文件元数据。
10. 删除文件前检查引用关系。

数据库事务和文件系统不是同一个事务，上传、删除必须设计失败清理机制。

## 10. 配置文件规范

配置文件：

```text
application.yml
application-dev.yml
application-test.yml
application-prod.yml
```

规则：

- 开发环境使用 dev。
- 测试环境使用 test。
- 生产环境通过环境变量显式指定 prod。
- 不允许生产环境默认使用开发配置。
- 数据库密码不能硬编码。
- 生产环境不能使用默认弱密码。
- 生产环境启用 HTTPS。
- MySQL 不应直接暴露到公网。

## 11. 测试规范

使用 JUnit 5。

每个业务模块至少测试：

1. 正常创建。
2. 正常查询。
3. 正常修改。
4. 正常删除。
5. 参数错误。
6. 资源不存在。
7. 跨用户访问。
8. 业务冲突。

重点测试：

- 用户数据隔离。
- Session 登录和登出。
- 日记日期修改。
- 知识笔记删除。
- 学习记录保留。
- 人生阶段删除。
- 时间线聚合。
- 照片权限。
- 数据导出和恢复。

后端提交前执行：

```bash
mvn clean verify
```

前端提交前执行：

```bash
npm run build
```

## 13. 协作规范

为确保代码风格一致、边界清晰，所有参与本项目开发的协作者必须遵守以下约定：

1. 开发前阅读四份基线文档。
2. 不得擅自改变数据库结构。
3. 不得擅自改变公共 API。
4. 不得擅自引入新的中间件。
5. 不得一次性重构整个项目。
6. 每次只完成一个明确模块。
7. 每个模块必须提供测试。
8. 每次修改必须列出文件清单。
9. 遇到需求冲突必须先讨论确认，不得自行猜测。

每个模块的开发流程：

```text
阅读需求文档
      ↓
分析数据库结构
      ↓
确定 API 接口
      ↓
列出需要修改的文件
      ↓
生成代码
      ↓
执行测试
      ↓
输出修改清单
      ↓
人工阅读和验收
      ↓
进入下一个模块
```

## 14. 模块验收标准

一个模块只有满足以下要求才算完成：

- 功能符合 PRD。
- 接口符合 API 文档。
- 数据库符合设计文档。
- 代码符合开发规范。
- 参数校验正常。
- 异常处理正常。
- 用户数据隔离正常。
- 测试通过。
- README 或相关说明已更新。

**不能仅以"代码可运行"作为模块完成的标准，必须逐项满足上述清单并通过人工验收。**

## 附录：四份文档的使用方式

建议严格按照以下顺序使用四份基线文档：

| 顺序 | 任务 | 执行者 |
| --- | --- | --- |
| 1 | 审核四份文档，确认需求 | 共同评审 |
| 2 | 根据数据库设计生成完整 SQL、ER 图和 Flyway 迁移 | 工具生成 |
| 3 | 根据 API 文档生成 OpenAPI / Swagger 配置 | 工具生成 |
| 4 | 整改现有基础框架 | 工具生成 |
| 5 | 生成阶段、日记 CRUD | 工具生成 |
| 6 | 阅读、运行、理解代码 | 开发者 |
| 7 | 继续生成知识库等 CRUD | 工具生成 |
| 8 | 开发时间线、搜索、导出等核心业务 | 开发者 |

"工具生成"指借助代码生成工具或脚手架完成，成果仍需人工评审验收；方案评审与核心业务开发由开发者完成。

补充说明：

- 人生阶段的照片关联需要增加 `PUT /life-stages/{id}/media` 接口，与数据库中的 `life_stage_media` 表对应。该补充已并入《02-API接口文档》第 3 节。
- 四份文档一旦确定，不要在开发过程中频繁修改基础架构；发现业务规则确实不合理时，再统一更新版本。

最终目标：

能够看懂它的每一层结构，独立修改、维护和扩展它。
